Standard Operating Procedure

SOC Investigation Workflow

An end-to-end operational methodology for triaging, investigating, containing, and documenting security incidents in high-velocity SOC environments.

01
Stage 01 // Ingestion & Trigger

Alert Generation

▶

Analyst Action

Monitors centralized alert queues across SIEM correlation rules, EDR behavioral engines, and perimeter IDS/IPS sensors; acknowledges ingested security events within defined operational SLA windows.

🔍

Evidence Reviewed

Rule trigger logic, event timestamps, source/destination IP addresses, hostnames, impacted user accounts, and pre-calculated alert severity scores (Low, Medium, High, Critical).

✓

Expected Outcome

Alert acknowledged, ingestion validated against known noise thresholds, and initial case ticket created with a unique incident tracking identifier.

02
Stage 02 // Validation & Scoping

Initial Triage

▶

Analyst Action

Conducts rapid verification to eliminate benign activity, authorized administrative changes, or false positives; evaluates asset business criticality to establish triage urgency and initial scope.

🔍

Evidence Reviewed

Asset classification tiers (Domain Controller vs. lab VM), user roles and behavioral baselines, IT change tickets, scheduled maintenance windows, and internal network architecture diagrams.

✓

Expected Outcome

Determination of False Positive (documented and closed with root cause) or True Positive (tagged for in-depth investigation and assigned priority level).

03
Stage 03 // Telemetry Deep-Dive

Log Investigation

▶

Analyst Action

Executes targeted SIEM queries (SPL/AQL) across correlated data sources to identify lateral movement, trace parent-child process lineages, and reconstruct a chronological event timeline.

🔍

Evidence Reviewed

Windows Event Logs (4624, 4625, 4688, 4720), Sysmon Process Creation (Event ID 1) & Network Connections (Event ID 3), firewall egress logs, DNS request archives, and proxy transaction records.

✓

Expected Outcome

Validated chronological incident timeline detailing patient zero, initial entry vector, executed binaries, lateral hops, and affected network segments.

04
Stage 04 // Correlation & ATT&CK Mapping

Threat Analysis

▶

Analyst Action

Analyzes extracted suspicious artifacts, maps observed adversary behaviors to the MITRE ATT&CK matrix and Cyber Kill Chain, and queries threat intelligence platforms for known adversary campaigns.

🔍

Evidence Reviewed

Cryptographic file hashes (SHA-256), command-line scripts, encoded PowerShell parameters, external C2 domain reputation scores (VirusTotal, AbuseIPDB), and active YARA rule matches.

✓

Expected Outcome

Cataloged Indicators of Compromise (IOCs), verified MITRE ATT&CK technique IDs (e.g., T1059, T1078, T1021), and characterization of the threat actor's capabilities and intent.

05
Stage 05 // Severity & Impact Assessment

Incident Classification

▶

Analyst Action

Evaluates the aggregate operational, technical, and regulatory exposure based on CIA triad impacts (Confidentiality, Integrity, Availability); assigns final standardized incident taxonomy.

🔍

Evidence Reviewed

Privilege level of compromised accounts, confirmed evidence of data staging or exfiltration, operational disruption of critical services, and compliance or privacy implications.

✓

Expected Outcome

Formal incident severity declaration (e.g., P1 - Critical Outage/Breach down to P4 - Informational Incident) and containment trigger criteria established.

06
Stage 06 // Containment & Action

Escalation / Response

▶

Analyst Action

Applies immediate operational playbooks for threat containment or escalates high-priority threats to Tier 2/3 incident responders, CSIRT leads, and system administrators with structured handoff briefs.

🔍

Evidence Reviewed

Containment approval matrices, host endpoint isolation telemetry, firewall blocklist propagation status, and Active Directory user session revocation verifications.

✓

Expected Outcome

Active threat vector neutralized: compromised endpoints isolated, unauthorized user credentials revoked, malicious external IP/domain blocks enforced on perimeter security controls.

07
Stage 07 // Reporting & Lessons Learned

Documentation

▶

Analyst Action

Compiles a formal post-incident investigation summary, documents root cause findings, audits chronological action timestamps, and recommends correlation rule tuning to mitigate recurrence.

🔍

Evidence Reviewed

Complete ticketing journal, IOC tables, analyst remediation logs, SLA metric logs, and false-positive/noise ratios for the triggering correlation rule.

✓

Expected Outcome

Resolved and archived incident report, updated detection signatures in SIEM/EDR, enriched SOC runbooks, and completed post-incident lessons learned review.

CASE #01 Simulated Lab
Identity & Access Monitoring

Multiple Failed Authentication Attempts

Investigation of an automated SIEM threshold alert triggered by over 60 failed logon attempts within 3 minutes from a single internal workstation targeting domain credentials.

Primary Tool: Splunk Enterprise (SPL)
MITRE ATT&CK: T1110.003 (Password Spraying)
Read Full Investigation Report

1. Scenario

A threshold-based correlation rule in Splunk Enterprise alerted on abnormal authentication failures originating from an internal host (192.168.10.45 / WS-LAB-04), iterating through multiple departmental user accounts in an isolated Active Directory test environment.

2. Investigation Objective

Determine whether the activity represents an unauthorized password-spray attack, verify if any account credentials were breached, identify the originating process, and formulate containment actions.

3. Evidence Reviewed

Windows Security Event Logs (EventCode 4625 - Audit Failure; EventCode 4624 - Successful Logon with Logon Type 3 Network), Active Directory authentication logs, and endpoint Sysmon telemetry.

4. Tools Used

Splunk Enterprise SPL Windows Event Viewer Sysmon

5. Terminal Log Sample

splunk-auth-failure.log 
EventCode=4625 Type=Audit Failure User=finance_user01 WorkstationName=WS-LAB-04
SubStatus=0xC000006A (Bad Password) LogonType=3 IpAddress=192.168.10.45
EventCode=4625 Type=Audit Failure User=finance_user02 WorkstationName=WS-LAB-04
SubStatus=0xC000006A (Bad Password) LogonType=3 IpAddress=192.168.10.45
... [58 additional failed attempts across sequential accounts] ...
EventCode=4624 Type=Audit Success User=finance_user03 WorkstationName=WS-LAB-04
LogonType=3 IpAddress=192.168.10.45 TargetOutboundUserName=finance_user03

6. Investigation Steps

  1. Executed SPL query index=windows EventCode=4625 | stats count by TargetUserName, IpAddress, SubStatus | sort - count to isolate the attacker's source IP and targeted accounts.
  2. Queried for EventCode 4624 from 192.168.10.45 within the subsequent 30-minute window to check for successful authentications following the failed attempts.
  3. Identified that after 64 failed logons, user finance_user03 logged in successfully via Logon Type 3.
  4. Pivoted to endpoint telemetry on WS-LAB-04 to inspect running processes, uncovering a test automated script generating authentication requests.

7. Findings

  • Confirmed a simulated horizontal password-spray attack executed against domain accounts from internal workstation WS-LAB-04.
  • Target account finance_user03 utilized a common password that was successfully guessed, resulting in unauthorized network logon.

8. Relevant MITRE ATT&CK Techniques

T1110.003 Brute Force: Password Spraying T1078.002 Valid Accounts: Domain Accounts

9. Recommended Remediation

  • Immediately terminate active sessions and enforce password reset for finance_user03.
  • Enforce domain-wide smart lockout policies to prevent distributed password spray techniques.
  • Mandate Multi-Factor Authentication (MFA) on all internal service access.
  • Isolate host WS-LAB-04 to conduct malware hygiene and unauthorized tooling inspection.

10. Conclusion

The simulated attack demonstrated the vital importance of correlating failed authentication spikes with subsequent successful logins. Immediate triage and account credential containment neutralized lateral movement risk before privilege escalation could occur.

CASE #02 Simulated Lab
Network Forensics & C2

Suspicious Network Traffic

Investigation of repetitive, beacon-like HTTP POST transmissions from an internal endpoint to an unclassified external IP address, exhibiting fixed 60-second intervals.

Primary Tool: Wireshark / tcpdump
MITRE ATT&CK: T1071.001 (Web Protocols)
Read Full Investigation Report

1. Scenario

In a simulated enterprise subnet, an egress monitoring alert flagged continuous, non-interactive HTTP connections from endpoint 10.0.2.15 communicating with an external listener at 198.51.100.23 on port 80.

2. Investigation Objective

Perform deep packet inspection on the captured PCAP trace, extract payload artifacts, determine if sensitive data or host metadata was exfiltrated, and characterize the C2 profile.

3. Evidence Reviewed

Full packet captures (.pcap), firewall egress state logs, DNS resolver transaction records, and Sysmon Process Network Connection events (Event ID 3).

4. Tools Used

Wireshark tcpdump NetworkMiner VirusTotal (Simulated)

5. Terminal Log Sample

wireshark-stream-dissection.pcap 
Frame 142: 12:04:15.102 IP 10.0.2.15.49214 > 198.51.100.23.80: Flags [P.], seq 1:318
POST /api/telemetry/checkin HTTP/1.1
Host: 198.51.100.23
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Content-Type: application/x-www-form-urlencoded
Content-Length: 94

data=aG9zdG5hbWU9REVWLVRFU1QmYWNjb3VudD1sYWJfdXNlciZpcD0xMC4wLjIuMTU=
[Decoded Base64: hostname=DEV-TEST&account=lab_user&ip=10.0.2.15]

6. Investigation Steps

  1. Filtered the PCAP trace using Wireshark display filter http.request.method == "POST" && ip.dst == 198.51.100.23.
  2. Calculated delta timestamps between sequential packets, identifying a rigid 60-second beacon frequency without randomized jitter.
  3. Reconstructed the TCP stream for frame 142 to extract and decode the base64-encoded query parameters.
  4. Cross-referenced Sysmon Event ID 3 on endpoint 10.0.2.15, linking the network socket to an unauthorized PowerShell process executing a hidden background loop.

7. Findings

  • The endpoint was running a simulated Command & Control agent transmitting basic discovery telemetry to an external server.
  • No proprietary intellectual property or credentials had been exfiltrated beyond initial host identification metrics.

8. Relevant MITRE ATT&CK Techniques

T1071.001 Web Protocols (HTTP) T1041 Exfiltration Over C2 Channel T1082 System Information Discovery

9. Recommended Remediation

  • Implement perimeter firewall block rules targeting 198.51.100.23 and blackhole the associated domain.
  • Isolate host 10.0.2.15, terminate the unauthorized PowerShell process tree, and remove the scheduled startup task.
  • Enforce strict outbound HTTP proxy authentication and inspect SSL/TLS traffic for abnormal beaconing.

10. Conclusion

Deep packet analysis and timing delta evaluation successfully exposed simulated C2 beaconing. Payload de-obfuscation confirmed initial reconnaissance telemetry, enabling rapid perimeter blocking and endpoint isolation.

CASE #03 Simulated Lab
Perimeter & Reconnaissance

Port Scanning Activity

Investigation of an IDS offense flagging high-volume sequential TCP SYN probes targeting a virtual DMZ application server across multiple port ranges.

Primary Tool: IBM QRadar / Snort IDS
MITRE ATT&CK: T1046 (Network Service Discovery)
Read Full Investigation Report

1. Scenario

In a simulated lab DMZ, an intrusion detection system (Snort) coupled with IBM QRadar flagged an internal host (192.168.1.105) initiating rapid connection requests to server 192.168.1.200 across ports 1 through 1024.

2. Investigation Objective

Confirm the port scan methodology (SYN stealth vs. connect), determine which service ports responded with SYN-ACK, evaluate exposure risk, and verify host authorization.

3. Evidence Reviewed

Snort IDS alerts (ET SCAN Potential Nmap SYN Scan), IBM QRadar flow data (QFlow), firewall accept/drop logs, and server access journals.

4. Tools Used

IBM QRadar SIEM AQL Snort IDS Wireshark

5. Terminal Log Sample

snort-alert-aggregation.log 
[**] [1:2000537:8] ET SCAN Potential Nmap SYN Scan [**]
[Classification: Attempted Information Leak] [Priority: 2]
10/24-14:22:01.104 192.168.1.105:54210 -> 192.168.1.200:21 TCP TTL:64 Flags: [S]
10/24-14:22:01.105 192.168.1.105:54211 -> 192.168.1.200:22 TCP TTL:64 Flags: [S]
10/24-14:22:01.106 192.168.1.105:54212 -> 192.168.1.200:80 TCP TTL:64 Flags: [S]
10/24-14:22:01.107 192.168.1.200:80 -> 192.168.1.105:54212 TCP TTL:64 Flags: [S.]
10/24-14:22:01.108 192.168.1.105:54212 -> 192.168.1.200:80 TCP TTL:64 Flags: [R]

6. Investigation Steps

  1. Triaged the QRadar offense, running an AQL query: SELECT sourceip, destinationport, count(*) FROM events WHERE sourceip='192.168.1.105' GROUP BY destinationport ORDER BY count(*) DESC.
  2. Analyzed the TCP flag sequence in packet logs: observing SYN packets immediately followed by RST upon receiving SYN-ACK on open ports, confirming an intentional Nmap half-open stealth scan (-sS).
  3. Mapped target responses: server 192.168.1.200 acknowledged ports 80 (HTTP) and 443 (HTTPS), while all other requests received RST/ACK closures.
  4. Contacted asset management to correlate 192.168.1.105, determining it belonged to an unapproved device in the testing network.

7. Findings

  • Confirmed an unauthorized network reconnaissance scan mapping open services on server 192.168.1.200.
  • No exploitation attempt or secondary vulnerability probing occurred following the initial reconnaissance.

8. Relevant MITRE ATT&CK Techniques

T1046 Network Service Discovery

9. Recommended Remediation

  • Enforce network access control (NAC) to prevent unauthenticated physical or virtual hosts from joining internal subnets.
  • Implement stateful firewall ACLs blocking internal subnets from directly enumerating server infrastructure.
  • Configure automated rate-limiting thresholds to drop and alert on high-frequency TCP SYN bursts.

10. Conclusion

Early-stage detection of network reconnaissance via IDS correlation enabled prompt identification of an unauthorized scanning host, preventing further targeted exploitation against exposed web ports.

CASE #04 Simulated Lab
Host Hardening & Privilege Audit

Unusual Linux Privilege Activity

Investigation of an auditd alert on an Ubuntu server where a service account invoked root commands via misconfigured sudoers permissions and spawned an interactive shell.

Primary Tool: Linux CLI / Auditd / Wazuh
MITRE ATT&CK: T1548.003 (Sudo Caching)
Read Full Investigation Report

1. Scenario

In a Linux hardening lab, system audit logs flagged execution of elevated administrative commands by standard web service account www-data (UID 33), escaping restricted privileges into an interactive root shell.

2. Investigation Objective

Trace the privilege escalation vector, determine how the service account obtained root permissions, audit executed shell commands, and remediate the configuration flaw.

3. Evidence Reviewed

Linux authentication logs (/var/log/auth.log), auditd system records (type=EXECVE), /etc/sudoers policy definitions, and bash history files.

4. Tools Used

Linux CLI auditd / ausearch Wazuh EDR Bash

5. Terminal Log Sample

auth-auditd-execution.log 
Oct 28 16:30:12 srv-linux-lab sudo: pam_unix(sudo:session): session opened for user root by (uid=33)
Oct 28 16:30:12 srv-linux-lab sudo:  www-data : TTY=unknown ; PWD=/var/www/html ; USER=root ; COMMAND=/usr/bin/find / -name test -exec /bin/sh \;
Oct 28 16:30:45 srv-linux-lab auditd[1042]: type=EXECVE msg=audit(1698510645.102:412): argc=1 a0="/bin/sh"
Oct 28 16:30:52 srv-linux-lab auditd[1042]: type=EXECVE msg=audit(1698510652.180:413): argc=2 a0="cat" a1="/etc/shadow"

6. Investigation Steps

  1. Inspected /var/log/auth.log for recent sudo: events associated with UID 33 (www-data).
  2. Audited /etc/sudoers, identifying an insecure wildcard rule: www-data ALL=(ALL) NOPASSWD: /usr/bin/find.
  3. Queried system audit records using ausearch -m execve -ts today to reconstruct commands executed inside the spawned root session, identifying reads to /etc/shadow.
  4. Verified that no persistent backdoors, SSH keys, or secondary accounts were added to the system.

7. Findings

  • The service account successfully bypassed privilege boundaries using a known GTFOBins technique via find -exec /bin/sh granted by an over-permissive sudoers configuration.
  • The simulated attacker inspected sensitive shadow password hashes but had not yet modified files or established persistence.

8. Relevant MITRE ATT&CK Techniques

T1548.003 Abuse Elevation Control Mechanism: Sudo and Sudo Caching T1068 Exploitation for Privilege Escalation

9. Recommended Remediation

  • Remove the dangerous NOPASSWD: /usr/bin/find directive from /etc/sudoers using visudo.
  • Ensure web service accounts possess non-interactive shells (/usr/sbin/nologin).
  • Enforce system-wide password rotation for all accounts stored in /etc/shadow.
  • Implement Wazuh EDR alerting for shell spawning from non-privileged service daemon parent processes.

10. Conclusion

Auditing system execution logs rapidly traced privilege escalation to an over-permissive sudo entry. Revoking the misconfiguration, auditing shadow access, and enforcing least-privilege principles restored system integrity.
